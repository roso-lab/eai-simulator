# HeteroCoord 场景任务设计工作流与接手说明

更新：2026-10-13。

## 1. 接手目标

本工作负责把论文中的异构多机器人协作关系，逐场景转化为自然、可观察、后续可执行的 benchmark 任务设计。当前阶段不直接冻结坐标、机器人型号、时间阈值或物理技能；先确认任务语义、合同关系和外部验收证据，再交给语义地图、技能和 evaluator 开发者绑定。

接手者应继续完成：

1. 根据用户对具体场景的观察和想法，逐个编写任务卡；
2. 维护已确认合同覆盖，避免把候选或扩展计作已覆盖；
3. 为地图/技能开发者整理对象、区域、能力和外部证据需求；
4. 在实现条件就绪后，再将确认的任务语义迁移到可执行 catalog、oracle 和实验配置。

## 3. 每个场景的工作流

用户通常只会提供场景名、截图/渲染观察和一段自然语言设想。按下面流程推进。

### 3.1 区分证据层级

- 用户明确描述：可以作为本轮设计事实，但仍需后续物理绑定；
- 截图或机器渲染可见：记录布局和候选区域，不能据此认证对象可抓、门可开或机器人可达；
- 助手新增任务对象或规则：必须标成提案；
- 地图/技能/evaluator 实测通过：才可升级为已认证实例。

状态建议固定使用：备选素材、基于观察的提案、用户已确认任务语义、待地图/技能验证、已认证实例。

### 3.2 先确定终端价值

每个任务先说明为什么属于 Production/logistics、Service/operations 或 Living/public。最终目标必须是场景中的真实价值，例如房间可入住、聚会服务持续可用、访客到达正确区域，而不只是“机器人移动了物体”。一个正式实例只登记一个最终 domain。

### 3.3 写完整团队任务链

任务卡至少包含：

- 场景事实、来源和未知项；
- 共同目标；
- 必要任务分支及依赖；
- 所需能力与允许的能力重叠；
- 信息何时公开、何时需要现场发现；
- 责任、物体和资源如何接续；
- 外部可观察的成功、失败和恢复证据；
- 可选扩展与后续绑定需求。

机器人由被测系统从 `usd/robot` 候选池选择。示例型号只表达能力候选，不能写成固定角色，除非用户明确要求且配置已经登记。

### 3.4 映射合同，但不凑覆盖

检查关系是否真的成立：

- P1：多项必要义务有真实并行机会；
- P2 handoff：责任和必要状态跨执行者转移，接收方继续执行；
- P2 precedence：下游动作执行时，外部前置条件仍有效；
- P3-J：至少两个成员共同完成不可拆的联合义务；
- P3-S：在注册窗口内持续维持服务谓词；
- P4：有注册容量的真实资源，逻辑准入和物理占用均可观察。

复合合同必须满足交互语义，不能因为两个原语出现在同一长任务就自动成立。尤其注意：

- 并行分支最终都完成，不自动是 C-P1P2-01；必须汇合后发生必要责任交接；
- 交接和资源排他同时存在，不自动是 C-P2P4-01；资源准入必须是正式交接条件；
- 一组联合搬运和一项普通任务争用通道，不是 C-P3JP4-01；需要多组真实联合义务；
- 找到物品后让另一机器人去拿，是 P2 找物接力；没有持续服务谓词时不是 P3-S；
- 补给循环和共享台面同时存在，不自动是 C-P3SP4-01。

### 3.5 用户确认后才更新覆盖

助手提出的方案先标“提案”。用户明确接受宏观方向或核心关系后，才把任务卡升级为“已确认任务语义”并更新覆盖表。确认不等于物理认证：坐标、阈值、能力、oracle、common 配对和执行结果仍保持待验证。

## 5. 已讨论场景摘要

### home_02：宠物饮水与喂食准备

状态：任务大纲和双水源评价原则已确认。

- 饮水链：取水、交接运输、通过有效门状态、机械臂向宠物水碗倾倒；
- 食物链：有载荷能力的无人机取猫粮、交接运输、机械臂向食盆倾倒；
- 近水源需要门协助，远水源路线更直接；不预设唯一正确水源；
- 机械臂持碗时不能同时开门，允许先开门再取物或请求协助；
- 注意：cf2x 的“只能观察、无负载”是 room_02 的用户设定；home_02/house 如需吊运，必须选择真实具备载荷能力的其他飞行配置。

### house：庭院用餐与阅读准备

状态：宏观任务和双机器人搬桌已确认。

- 两个合格成员共同搬桌，单个合格成员搬椅；
- 无人机将水果送至庭院，书籍经门和台阶送到庭院阅读位置；
- 桌面稳定就位、门实际可通行等条件绑定到依赖动作时刻；
- C-P3J-01 需联合支撑、同步移动和稳定放置的外部证据。

### office：跨层会议准备与来访接待

状态：会议空间准备、跨层资料/补充物取送、入口接待三条工作线已确认。

- 二楼资料与第三层补充物形成真实楼梯竞争；
- 窄楼梯以地图确认的连续梯段登记容量 1；
- 逻辑准入、实际进入、带载完全退出和释放分别留证；
- 持续接待、成员退出和通信退化仍是可选扩展。

### room_01：别墅多客房入住准备

状态：任务大纲已确认。

- 分房间查找不同类别用品；
- 按单个客房配齐套件，在集配面汇合；
- 齐套后正式交给下游成员跨层运输并完成可取用布置；
- 这是 C-P1P2-01 的主要承载，需检查缺项放行、串房和责任遗漏。

### room_02：居家归整、空地查找与房间送物

状态：用户已确认场景事实并澄清找物接力意图，但当前覆盖审查尚未将整张任务卡计作已确认任务大纲。

- 门口散落鞋子归入鞋架；
- cf2x 只能观察、没有负载能力；它找到目标后报告位置，由其他机器人接续拿取并送到房间；
- Pepper 类高台操作候选从厨房取水果并送房间；
- 用户设定受限房间一次只能进入一个机器人，默认包括 cf2x；
- 找物接力是 P2，房间容量是 P4，二者分别登记；不构成 P3-S，也不自动构成 C-P2P4-01。

继续前可请用户确认是否将这三条工作线整体升级为 room_02 已确认任务大纲；确认后更新覆盖审查中的场景数量，但不会新增合同种类。

### room_03：家庭聚会窗口的餐厨侍应保障

状态：主方向和 C-P3S-01 持续服务语义已确认。

- 准备期布置饮品站/餐桌并清出主动线；
- T0–T1 服务窗口持续维持饮品站保有量和主动线可通行；
- evaluator 通过预注册的容器移除/隐藏事件模拟消耗，被测系统不知道事件时刻表；
- 按允许观测发现存量下降并执行多轮补给；最终状态不能抹去中途空窗；
- 迎宾换班、共享备餐台和成员退出均是未确认扩展。

## 6. 剩余四个合同的设计方向

这些是后续选场依据，不要求塞入下一个场景。

### C-P2P4-01

需要“取得共享资源使用资格”成为正式接收责任的必要条件，接收方在合法占用窗口内继续工作并释放资源。普通找物接力加房间排他不够。适合有装卸台、维护工位或受控操作区的任务。

### C-P3JP4-01

需要至少两组各自执行不可拆联合义务，并竞争同一容量受限通道或区域。容量单位要说明是机器人、协作组还是空间占用。不要让无事可做的机器人陪同以制造联合关系。

### C-P3SP2-01

需要在注册服务窗口内进行正式责任和状态换班，由接替者继续服务；服务空窗与交接是否合法分别测量。room_03 的迎宾换班可作为候选，但目前未确认。

### C-P3SP4-01

需要持续服务依赖有限共享资源，例如真实补给/充电资源和可行轮换计划。资源合法使用不能替代服务连续性证据。room_03 只有在共享台面或其他资源确实成为维持服务的有限条件时才可能扩展，当前未确认。

## 7. 与最新远端技能更新的衔接

2026-10-13 已把本工作 rebase 到远端 `origin/HeteroCoord` 基线 `7216b871`。该基线已包含地面/空中拓扑导航、Go2 多层路线、Pepper box transport、无人机 aerial pick/place 和 cooperative runtime 等更新。接手时应重新读取实际 capability profile 和 provider 约束，不能沿用任务卡中的型号示例作为已认证能力。

特别注意：远端 aerial pick/place 当前限制于相应的 Iris/Pegasus position-robot 配置；cf2x 在 room_02 中仍按用户指定的观察型、无负载成员处理。任务设计允许提出能力需求，但具体机器人、控制器、载荷范围、室内航线和物体接口必须通过当前代码与物理验证。

## 8. 接手后的建议顺序

1. 读完本文件和两份权威设计文件；
2. 检查 `SCENE_TASK_OUTLINES.zh-CN.md` 中 room_02 的当前状态，必要时只向用户确认是否整体采纳；
3. 从 room_04 或用户下一个提供观察的场景继续，不按剩余合同反向编故事；
4. 每个场景确认后同步更新具体任务卡、30 场景总表和覆盖审查；
5. 地图/技能条件就绪时，另建可执行实例绑定，不直接修改语义结论；
6. 提交前运行 `git diff --check`，核对“提案/已确认/已认证”状态没有被混用。
