# 30 锚点合同底稿编写委托书（剩余 24 个锚点）

日期：2026-10-24
委托人：出题人（项目负责人）
执行：论文/场景协作者
验收：出题人逐条拍板（绑定权不在协作者）；工程侧做结构校验

## 一、背景与目的

HeteroCoord 基准共设 30 个"场景任务锚点"（anchor，一道标准考题 = 一个场景 × 一个任务设计 × 一套协调考察点）。目前 **6 个试点锚点已完成全链**：义务图、里程碑、能力对应、资源约束、谓词（机器可判的判分点）均已成文并实现为可执行的 oracle 判定器（6 锚点共 19 条谓词，2026-10-23 由出题人亲自绑定语义）。

现在需要把**剩余 24 个锚点**的合同**底稿**编写出来。底稿的作用：把每个锚点从"一句话目标"细化为"可绑定、可实现、可认证"的完整任务定义，供出题人做最终语义拍板，随后进入工程实现。

**分工边界（重要）**：
- 协作者：编写底稿——把考法写细、把谓词和它的"待填空"列全；
- 出题人：对每条谓词做最终绑定（事件对怎么定、阈值定多少、身份怎么映射）——**底稿中所有数值/语义决定均以"建议值"形式给出，留出题人裁决**；
- 工程侧：结构校验 + 实现（本委托不涉及代码）。

## 二、每份底稿必须包含的七个部分

以已完成试点 `prod-p1-01`（工厂 A 线拣货清点，P1 互补并行）为粒度基准：

| 部分 | 内容 | 试点示例（prod-p1-01） |
| --- | --- | --- |
| 1. 任务故事 | 3–5 句话讲清任务全过程与考察点 | 拣两批独立物料，过同一扫描工位，两批可并行，拣完清点核对后发货 |
| 2. 义务图（obligations） | 谁必须完成哪些工作单元；义务间有无先后/并行结构 | work_unit_a、work_unit_b（可并行）、reconcile_units（在两者之后） |
| 3. 角色与能力 | 参与角色清单 + 每个义务需要的能力（对接机器人简历词汇表：mobile_base、barcode_scan、payload_transport、inspection_camera、service_interaction、synchronized_motion 等） | picker、counter；mobile_base + barcode_scan |
| 4. 里程碑（milestones） | 有序的里程碑标签 + 每个里程碑的**外部可观测定义**（评估器从观测/账本可查证，不能依赖被测系统自报） | assigned → both_lots_picked → count_reconciled → accepted |
| 5. 资源与区域 | 任务涉及的物理资源（工位/柜台/泊位/通道/隔离位等）、容量、互斥关系；**区域实体的场景侧描述**（位置描述 + 建议命名，精确坐标出题人另行与语义地图对齐） | 扫描工位 ×1，容量 1，批次互斥 |
| 6. 谓词清单（重点） | 这道题的机器可判判分点，每条含：名字（英文蛇形）、考察内容（中文）、**判法类型**（见第三节六类原语）、建议的事件对/阈值（标注"待出题人裁决"） | lot_a_and_lot_b_may_run_in_parallel（行为体现，区间重叠≥1 拍）等 3 条 |
| 7. 难度与设计意图 | 该锚点考察的协调难点、预期失败模式（含"故意不可行"的 D1 考察材料如有） | 并行机会利用不足 → 串行浪费时间；互斥违规 → 两批同时占工位 |

## 三、谓词判法只从这六类原语中选（已实现，可直接复用）

| 原语 | 判什么 | 已绑定示例 |
| --- | --- | --- |
| 区间重叠（min_overlap） | 两段执行区间是否有足够重叠（考并行） | 两批拣货并行，≥1 拍 |
| 严格先后（precedence，可选时限） | B 必须严格晚于 A，可选"N 拍内"上限 | 核对必须在两批完成后 500 拍内开始 |
| 双事件窗口（within_window） | 两事件时刻差 ≤ 窗口 | 左右搬运员起抬差 ≤250 拍 |
| 覆盖空窗（coverage_no_gap） | 时域内无资源的空窗 ≤ 上限 | 通道清点空窗 ≤50 拍 |
| 区间互斥（zone_mutex） | 同一区域不同占用者的区间不得重叠 | 工位/隔离位/服务台/泊位/扫码点容量 1 |
| 接触计数（contact_count） | 区间内任意时刻保持接触的实体数 ≥ N | 托板搬运期间承托者 ≥2（允许替补） |

特殊判法需求（六类覆盖不了的）请在底稿中显式标注"新原语提案"并说明，不要硬套。

## 五、编写规则与禁区

**必须**：
1. 谓词命名用英文蛇形（如 `pallet_release_before_second_load`），判法从六类原语选；
2. 里程碑必须给"外部可观测定义"（例："两批拣完 = 两批末件均完成扫码的观测事件"，而不是"系统报告拣完"）；
3. 每条谓词给建议参数（事件对、阈值拍数，1 拍 = 0.02 秒）并标注 `[待出题人裁决]`；
4. 每个资源区域给"建议命名 + 场景内位置描述"（如 `scan_station`：仓库主通道北侧扫码台周围约 1 米范围）；
5. D1 考察材料（故意不可行的任务/义务）要显式标注"设计上不可行，预期安全拒绝"。

**禁止**：
1. 不做最终绑定决定——所有数值语义只给建议值；
2. 不声称任何认证/资格（certification 概念不存在于底稿层）；
3. 不修改 6 个已完成试点、不修改任何代码/论文/目录文件；
4. 不引入被测系统可见的提示性协议（资源约束写给评估器，不写给被测系统——被测系统只能从任务描述知道"这里一次只能进一个"）。

## 六、交付方式与验收流程

1. **格式**：每锚点一份 Markdown 章节或一个 JSON 对象（推荐 JSON，字段照试点合同结构：anchor_id / story / obligations / roles / capabilities / milestones / resources / predicates[] / difficulty_notes；谓词字段：id / kind(六类之一) / checks(中文) / suggested_event_pair / suggested_thresholds / status="draft"）；
2. **先交样稿**：先交 **2 份**（建议 prod-p4-01 和 svc-p3-02，一个纯 P4 一个 P3-S，覆盖面最广）供出题人确认风格，再批量交其余 22 份；
3. **验收**：出题人逐锚点、逐谓词拍板（预计每锚点一轮问答）；工程侧随后做结构校验与 oracle 接线；
4. **放置**：交付物放入 `benchmark/docs/anchor_drafts/` 目录（每锚点一文件），通过 GitLab 推送，**不要**改动其他目录。

## 八、常见问题

- **问：一个锚点该有几条谓词？** 答：试点为 3–4 条；建议每锚点覆盖其关系签名（P1→重叠类、P2→先后类、P3-J→窗口/计数类、P3-S→空窗类、P4→互斥类），复合锚点（如 P1+P4）每类至少一条。
- **问：场景里没有对应道具怎么办？** 答：底稿照写，在资源部分标注 `[场景缺口：建议补充 XX 道具]`，出题人汇总后与语义地图一起处理。
- **问：和语义地图（场景实体 ID）什么关系？** 答：底稿给"建议命名+位置描述"，语义地图最终给精确坐标——两者在出题人处合流为 identity_mapping。
