## 用户观察驱动的逐场景工作流（2026-10-12，用户指定）

1. **用户提供场景与想法。** 用户说出场景名，用自然语言描述自己看到的区域、楼层、通道、物体和限制，以及想到的任务。不要求一次填完整表格、不要求先提供地图或坐标。遇到同名场景时先澄清具体目录。
2. **整理事实与未知。** 主代理简短复述与任务有关的观察，区分“用户观察”“用户任务设想”“助手推测”“待工程验证”。看得到货箱不等于已能抓取，有楼梯不等于机器人已能上下楼；未知信息不自动补成事实。
3. **围绕用户任务做 benchmark 整理。** 保留原始意图，整理三大类归属及终端目标、完整团队任务链、能力组和信息流、合同候选、可观察的完成/失败/接续证据及测量问题。用通俗语言解释为什么对应某合同；不机械套满 P1–P4 或 D1–D6。检查是否只有多个独立单机动作、交接是否必要、信息是否实际需要获取，以及是否自然形成异构协作。
4. **提出有依据的扩展。** 原始任务与扩展分开，通常提出一至三个有价值的方向，说明利用了用户描述的哪个场景特征、补充什么协作测量、还依赖什么能力。缺乏场景依据的不当作推荐任务；新增对象、技能或事件显式标注为待建设。机器人池自主调度、真实空间成本和公开信息权限沿用既定原则。
5. **只追问关键问题。** 优先用已有描述推进；确有影响任务成立或分类的缺口时，一次询问一个关键问题。用户确认的是哪一层就只记录哪一层，不能把宏观认可提升为地图/技能认证。
6. **记录并移交后续绑定。** 在本文件追加或修订该场景任务卡，保留观察来源、原始想法、已确认主任务、可选扩展和待验证事项。其他开发者完成语义地图后再选点、绑定对象/机器人、细化阈值并认证；本阶段不部署场景、不改运行 catalog、不向协作者自动发送消息。

用户输入可以很简单：“场景是……；我看到……；我想让团队完成……”。主代理每轮输出以“场景理解 → 用户任务的团队流程 → 合同/测量依据 → 可选扩展 → 必要时一个问题”为顺序，避免反复解释已确认规则。

记录状态分别为：备选素材、基于观察的提案、用户已确认任务语义、待地图/技能验证、已认证实例。已有 30 行均仍为备选素材，只有经过上述流程的具体内容才能升级状态。

## home_02 用户场景任务卡：宠物饮水与喂食准备

状态：2026-10-12 当前阶段任务大纲与双水源评价原则已确认，记录可移交后续地图/技能绑定；未完成物理实现认证、阈值冻结或 common 配对认证。已确认轻载吊运、机械臂倾倒、持碗时不能同时开门、猫粮无需开包，以及任务正确性与多维成本分别评价。用户后续明确允许先自行开门再取物，也可求助；门可能自动回关，具体条件待登记。此卡取代下方 home_02 泛化候选行，其他场景不照搬；未确认的事件扩展仍单列。

**观察与来源。** 场景身份为 `usd/scene/Living and public space/home_02`。用户截图 `/tmp/codex-clipboard-dcd4076e-f29b-4159-a326-8ff70ad6390f.png` 可见多个房间、隔墙、连接开口、卫生间样式区域及较大公共区域。用户补充：有两处距离不同的取水点，厕所洗手台较高，高货架上有猫粮，客厅有目标宠物碗，房门需要带机械臂机器人协助打开。后几项作为用户描述记录，图片本身不能认证水源可交互、门可转动、食物可抓取或液体可倾倒。

**用户原始设想。** Pepper 在高洗手台接水并交给小车运输；带机械臂成员协助开门；最终倒入客厅宠物水碗。无人机从高货架取猫粮、放到小车上，再运到猫粮盆倾倒。

**类别与团队终端目标（建议）。** Living/public：在家庭访问与安全约束下，使宠物能够在指定位置获得适量饮水和食物，保持相关通路和使用区域可用。两个补给分支共同满足生活照料目标，不以“容器送达”代替完成，不要求模拟宠物进食。若实例最后仅保留货物运输而去掉生活可用性目标，需重新核对领域归类。

**两条任务链。** 饮水：选择可用取水点与合格成员 → 获取/使用合适接水容器 → 接水 → 合法装载与配送责任交接 → 在相关房门已可通行时运输 → 由机械臂在目标水碗完成倒水。食物：定位/核验猫粮 → 具备轻载吊运能力的无人机取下猫粮 → 稳定放置并交接给运输成员 → 经必要开门协助送到喂食区域 → 由机械臂将食物倒入目标食盆。用户明确猫粮无需开包，不添加开包义务。开门是所影响路径的前置条件，不强行给两条链都增加无实际作用的开门步骤；分支间真实资源竞争单独记录。

**机器人和能力边界。** 用户指定默认无人机具备吊运轻型资产的能力，此能力应写入对应实例简历，后续核验载荷范围与实现，不再作为宏观任务是否可选的悬而未决项。倾倒由机械臂完成，小车承担运输；猫粮按可直接倾倒的任务物料处理，不设计包装开启。高洗手台仍需合格机械臂的可达性、抓持及取水接口。高度本身不证明只有无人机能完成；其他真实合格候选仍按池规则调度。

**持碗与开门的执行约束（用户确认并补充）。** 机械臂持碗时操作能力被占用，不能同时开门；若此时门关闭且没有合法可用的自助操作方式，需要另一名具备开门能力的成员协助。用户明确允许先自己打开门，再进去取物并出来；不能将调用另一台机器人设为所有执行的成功条件。门可能自动回关，历史开门记录不保证当前可通行。该约束只绑定实际持碗区间与所用操作资源，不是机器人永久禁止开门，也不是一律要求开门者必须用不同型号。若要放下容器后自行开门，必须有合法放置面、物理状态变化和拾取代价；是否允许该替代方案须后续登记，不能靠释放软件锁让容器凭空悬置。持碗与运输载具的具体装卸边界后续据地图/技能落实，不强制增加没有实际作用的交接。

**合同与测量候选。**

- C-P1-01：水与食物均为必要贡献；只有能力和资源配置确有并行机会时才登记并行关系，共享一台运输车造成部分串行需在完整图中保留。
- C-P2-01：取水/取粮后移交物品、目标及残余工作给运输或倾倒成员。仅物体接触或同一机器人继续工作不能伪造跨成员责任交接。
- C-P2-02：开门使后续通行可行，通行时门的状态须仍有效。是否开门后保持开启，或必须持续扶门，尚待用户/地图确认；后者需要另审持续服务窗口，不能自动叫作联合搬运。
- C-P4-01：仅在多个真实任务竞争同一门口、装载位或操作区且有合法容量约束时适用。门窄、门关闭或需要机械臂本身不足以成立排他。
- 全任务首先是典型家庭任务；common 候选可来自前置或交接阶段，但不把两分支并行自动等同于 C-P1P2-01，除非确有汇合后的必要责任交接。

规划测量关注能否选出合格机器人、水源与工作安排；关系测量关注门状态、真实交接与残余任务接续；终端证据关注目标碗中实际可用的水/食物量及注册的溢出、错盆等条件。水源距离通过真实路径、速度、门操作、等待和倾倒等影响进度与成本，不能直接以“选最近水源”判成功。事件扩展后按既定 D2/D4 规则建面板，D5 仍需跨域配对认证，D6 不新增未经审定的混合总分。

## house 用户场景任务卡：庭院用餐与阅读准备

状态：2026-10-12 用户认可宏观方向，并补充桌子可采用双机器人搬运、椅子由单机器人搬运。记录为包含联合搬桌的任务大纲；具体目标桌、物理参数、门行为条件及地图/技能认证仍待落实。替代下方 house 泛化行作为当前讨论入口，未确认的事件扩展仍单列。

**共同目标（建议）。** 归 Living/public：把住户指定的室内相关区域整理到要求状态，并准备好庭院用餐/阅读区域，使桌椅和通路可用，指定水果及书籍实际放到可取用位置。明确哪些整理工作是住户独立要求、哪些是为后续取放/通行建立前置条件，不能随意安排无关家具移动只为增加机器人数量。

**任务分支。** ① 空间整理：按公开目标状态调整指定桌椅/物品，保留出入口与必要通路，准备庭院目标放置面。② 水果：厨房选取指定水果或轻载容器 → 由已设定具备轻载吊运能力的无人机获取/接收 → 沿实际可飞、可出入的路线运到庭院 → 稳定放在指定桌面，或交给合格接收成员完成摆放。是否需额外成员装载由吊点/容器与技能决定，不自动增加。③ 书籍：从书架获取指定书籍 → 自行跨越合格路径或交给具备台阶通行能力的成员 → 经当前可通行的门送到庭院 → 放入指定阅读位置。不得只以无人机悬停或机器人到达室外判交付完成。

**桌椅搬运（用户补充确认）。** 在需要调整桌子位置的整理任务中加入双机器人联合搬桌；椅子由一个具备相应能力的机器人搬运。桌子绑定为需要两个合格参与者共同支撑与协调移动的对象，具体重量、尺寸、抓持位置及单体能力约束后续验证，不能仅凭外观宣称物理必需。由被测系统从机器人池选择两名参与者，不固定型号/身份；两者就位并建立合法支撑后，在注册同步窗口与联合状态约束内搬运，最后稳定放置并解除支撑。轮流搬、一个搬另一个旁观不能算联合完成。椅子允许单体完成，不要求另一成员陪同，也不因两台机器人分别搬两把椅子就登记 P3-J。

**流程关系。** 分支准备在真实能力与资源允许时可以并行。两名成员搬桌时占用相应操作资源，其他合格成员可搬椅、取书或准备水果；不能让同一机械臂在支撑桌子的同时开门或执行其他不兼容工作。若这张桌子是水果/书籍的最终放置目标，先稳定就位再允许最终摆放，提前取物和运输到合法等待点仍允许；不假设所有物品都必须放在该桌上。若桌面或通路需要整理，最终摆放/通行等待对应条件成立，不强行要求整个整理分支完成后所有运输才启动。台阶产生载荷状态下的可达性要求，与门的开闭条件分开检查。无人机在室内外如何转接、物体形态和目标承载面待地图/技能绑定，不假设飞行能绕过所有门。

**门的时变前置条件（同样修正 home_02）。** 用户允许先开门后取物、也允许呼叫其他成员开门。合同要求实际通行期间满足所需净空与安全条件，而非要求调用某个助手或保留历史“开门完成”标志。门若自动回关，需要重新确认、重新开门、安排协助或采取其他允许的合法策略。建议将“开启后保持”和“注册规则下自动回关”作为可分辨条件；关闭触发、延迟、可见信息与安全应对机会后续登记，不能事后任意关门制造失败。普通门回关不自动构成成员重配置 D4 主面板或 P4 资源冲突。

## room_05 用户场景任务卡：家庭来客接待与空间恢复

状态：2026-10-14 用户确认家庭来客接待任务。任务包含迎客入座、饮品与风扇准备、卧室整理、客人离开引导，以及饮品返回冰箱。用户特别确认厨房较窄、需要取三至四件物品；客人离开时，冰箱回收遵循“一个机器人开冰箱并退出，另一个机器人进入放置饮料，最后关冰箱门”的顺序。具体物品、客人行为、厨房容量、门行为、机器人能力和外部验收仍待地图/技能/evaluator 绑定。

**场景与共同目标。** 场景为家庭环境，任务涉及大门、客厅、厨房、卧室和冰箱。客人到访期间，团队要让客人安全进入并坐到客厅指定位置，把指定饮料或红酒放到客厅茶几，把客厅角落的风扇移到客人旁边，同时完成卧室内的收拾：把书包挂到指定挂钩，把床上的登记物品放入对应柜子。客人离开后，团队要打开大门并引导客人离开，再把饮料收回厨房冰箱并关闭冰箱门。

**阶段与时序约束。** 只冻结必要的先后关系，具体秒数和窗口长度后续注册。

1. **迎客阶段：** 客人在大门外等待。大门必须先达到可通行状态，客人才能跨过门槛；机器人继续引导，直到客人到达并坐到指定位置。仅打开门或机器人走到客人旁边不算迎客完成。
2. **接待与整理阶段：** 客人入座后，风扇才进入“移到客人旁边”的验收窗口；指定饮料应在客人离开前放到客厅茶几。取饮料、搬风扇和卧室整理可以在不影响客人通路的条件下并行。厨房取物可分成多次动作，但每次进入、取放和退出都必须遵守厨房容量。
3. **离开阶段：** 只有在注册的离开触发条件成立后，机器人才能把客人引导出门。大门必须先重新达到可通行状态，客人才能向外通过；客人完全离开后，离开引导才算完成。大门是否需要最后关闭暂不纳入任务，除非后续另行确认。
4. **饮料回收阶段：** 饮料回收可以和客人离开引导并行，但冰箱操作保持固定顺序：机器人 A 进入厨房并打开冰箱，确认门已打开后完全退出厨房；只有 A 释放厨房进入空间后，机器人 B 才能进入并放回饮料；最后在最后一件饮料已经稳定放入且操作区域安全时关闭冰箱门。若饮料分批回收，每一批都要保留对应的进入、放置和关门证据，不能用最后一次关门覆盖中途违规。

**合同候选与边界。**

| 合同候选 | 本场景的对应关系与检测目的 |
|---|---|
| C-P1-01 | 迎客、厨房取物、搬风扇和卧室整理是共同目标下的互补工作；只有任务配置确实提供并行机会时才登记并行关系。 |
| C-P2-02 | 大门达到通行状态是客人进入/离开的前置条件；冰箱门打开是另一机器人放回饮料的前置条件；执行依赖动作时必须重新确认条件仍有效。 |

| C-P4-01（条件候选） | 厨房较窄，只有在多个有真实任务的成员竞争同一进入空间、冰箱操作区或门口，且能记录准入、进入、占用、退出和释放时才登记排他资源。 |
| C-P2P4-01（待审定候选） | 只有当“取得厨房/冰箱合法使用资格”被注册为接收放置责任的必要条件时，才将冰箱回收序列登记为资源约束下的责任交接；单纯先后进入不自动满足该复合合同。 |

## room_06 用户场景任务卡：跨层图书接力与重物联合搬运

状态：2026-10-14 用户确认两层复式家庭场景任务。场景有天井区域、没有楼梯，一楼和二楼都有书架。任务包含二楼书籍经机械臂机器人和无人机接力转移到一楼书架，以及一个超过单个机械臂载重、但不超过无人机载重的物体，由两个机械臂机器人同时搬运。书籍阶段和重物阶段串行执行，不要求并行。具体书籍、重物、传递面、载重、飞行边界、机器人能力和外部验收仍待地图/技能/evaluator 绑定。

**共同目标。** 完成家庭图书重新归位，并把登记的重物安全移动到指定位置。书籍必须真正放入一楼书架，重物必须由两名合格机械臂成员共同完成稳定搬运和放置；只到达楼层、只放到临时桌面或只发出完成消息都不算任务完成。

**阶段一：书籍跨层接力。**

```text
登记二楼目标书籍
→ 二楼机械臂机器人从书架取书
→ 放到二楼指定平地或桌面
→ 无人机确认书籍稳定并取走
→ 通过天井运到一楼
→ 放到一楼指定平地或桌面
→ 一楼机械臂机器人接收
→ 放入一楼书架的正确位置
```

书籍身份、数量、目标书架位置和剩余工作随每次必要交接传递。二楼机器人必须先完成稳定放置，无人机才能取书；无人机取走后，二楼传递面才能再次使用。无人机在一楼稳定放置后，一楼机械臂机器人才能接收；接收完成后，一楼传递面才算释放。没有楼梯时，跨层路径必须由天井的真实飞行路线或后续认证的其他设施提供；天井开放外观本身不等于无人机已经获得飞行许可。

**阶段二：重物联合搬运。**

本版将重物分支限定为同一楼层内的搬运，避免在没有楼梯的场景中虚构地面机器人跨层路线。两个机械臂机器人必须同时到达物体两侧，建立注册的共同支撑，在同步窗口内抬起、移动并稳定放置，最后解除支撑。单个机械臂的载重能力不足以独立完成该物体；两台机械臂的组合能力必须经过配置和物理验证。无人机虽然登记的载重上限可以覆盖该物体，但若任务要求双机械臂联合搬运，就必须同时登记无人机不能替代的约束，例如物体抓取接口、尺寸/稳定性、室内飞行规则或任务安全规则；否则系统可以绕开 P3-J，联合搬运就不是必需义务。

重物阶段不得以轮流搬、一个机器人搬另一个机器人跟随、或一台机器人短暂接触来替代联合动作。外部验收需要确认两名成员的实际接触/支撑、同步抬起、共同移动、稳定放置和释放顺序。

**两个阶段的时序。** 书籍阶段和重物阶段按实例预注册的顺序串行执行；本版不把它们作为并行机会，也不把不同顺序混入同一个统计样本。阶段一必须完成书籍身份、数量和一楼书架归位检查，相关无人机和传递面释放后，阶段二才能开始。重物阶段必须完成稳定放置或注册的安全停止后，整个任务才结束。具体阶段时限和等待上限待地图与技能绑定。

**合同候选与边界。**

| 合同候选 | 本场景的对应关系与检测目的 |
|---|---|
| C-P2-01 | 书籍从二楼机械臂成员交给无人机，再由无人机交给一楼机械臂成员；交接必须包含书籍身份、目标位置、已完成与剩余工作。 |
| C-P2-02 | 二楼/一楼传递面必须先达到可用状态，书籍才能在对应位置交接；无人机必须在合法天井路线和公开许可范围内执行跨层动作。 |

当前不登记 C-P1-01，因为书籍阶段和重物阶段明确不并行；也不登记 P3-S。若书籍阶段内部未来采用多本书的流水推进，需要另行确认是否有真实并行机会，不能由多个物品自动推出 P1。

**完成判据。** 二楼登记书籍全部从目标书架取下并通过合法天井路线到达一楼；一楼机械臂实际接收并按身份、数量和目标位置归入书架；重物由两名机械臂成员共同完成同层搬运并稳定放置；不存在漏书、错书、重复放置、单臂替代联合搬运或无人机绕过注册限制的情况。记录书籍各段交接、飞行和等待时间，以及重物双臂同步、移动、放置和安全状态证据。

**待后续绑定。** 二楼和一楼书籍对象及书架位置、二楼/一楼传递面、天井净空和飞行边界、无人机取放接口、两类机械臂的书籍操作能力、重物质量/尺寸/抓取位置/双臂支撑规则、重物同层起点与终点、无人机不能替代双臂的注册约束、阶段顺序和时限。


酒水、杯子和二楼物品是同一订单服务中的不同工作项；只有在任务配置确实提供独立能力、空间和时间机会时才并行。进入吧台窄通道的容量限制适用于真实占用区间：机器人必须完成进入、通过、退出并释放通道，不能只凭预约或发送消息提前释放。具备爬楼能力的机器人可以直接完成二楼取物；楼梯口交接是允许的替代方案，不是固定角色要求。

## factory 用户场景任务卡：火灾救援与动态障碍协作

状态：2026-10-15 用户确认 factory 复用 `benchmark-task` 分支 `demo/fire_rescue` 的任务框架。该框架提供火灾救援的任务分配、导航、机械臂动作、动态障碍救援、任务检查点和统一成功判定；本卡把它整理为 benchmark 的场景语义。`fire_rescue` 中的机器人型号、固定坐标、火源/按钮/灭火器数值和控制器实现只作为示例，不直接冻结为最终 benchmark 配置。

**共同目标。** 工厂内出现登记的火源后，多机器人在安全约束下完成现场侦查、救援通道开启、现场数据采集和灭火器运送；如果运行中登记的动态障碍阻塞关键通道，还必须完成清障、恢复受阻任务，并在所有必要条件满足后结束任务。

**参与能力。** 任务按能力简历选择机器人，不按型号硬编码角色。需要的能力包括：复杂地形或障碍通行能力、移动底盘、机械臂抓取与按压、现场图像/雷达等传感器、灭火器稳定携带，以及必要时清除通道障碍的操作能力。示例实现中，M20 适合复杂地形和灭火器抓取，Carter 适合平地传感器采集，Scout＋机械臂适合按压救援通道按钮和清障；最终场景应由实际机器人池绑定这些能力。

**四条基础工作线。**

1. **火源侦查：** 前往火源附近的登记侦查区域，确认火源位置或状态并回传侦查结果。完成条件是到达合法区域并提交可核验的侦查事件；只到达附近、发送空消息或读取 evaluator 隐藏真值都不算完成。
2. **开启救援通道：** 前往登记的救援通道按钮，由具备机械臂和按压能力的机器人完成按压。通道状态必须由外部场景确认已经打开，按钮附近的到达或“已发送按压命令”不能替代实际开启。
3. **现场数据采集：** 搭载登记传感器的机器人到达现场，采集图像、雷达或其他登记数据并回传。到达采集点但没有有效数据记录不算完成；数据任务可以与侦查、通道开启和灭火器准备并行，前提是路线、能力和资源确实独立。
4. **灭火器运送：** 具备机械臂的机器人到达灭火器位置，完成接近、抓取、抬升和稳定携带，再把灭火器运到火源附近。抓取完成但未保持携带、只到达取件点或把灭火器放在中途位置都不算完成。

**基础时序。** 火源生成并登记任务 → 系统依据能力和位置分配四条工作线 → 侦查、数据采集、通道开启和灭火器准备在允许时并行 → 通道打开后，依赖通道的后续进入/运输才可继续 → 灭火器保持有效携带并到达火源区域 → 至少三台登记机器人到达火源附近并完成必要现场集结 → 若没有动态障碍，直接进入成功判定；若发生障碍事件，先完成下述救援流程，再判定成功。

**动态障碍救援时序。** 障碍必须是任务配置中登记的真实事件，不能只因为地图里存在物体就算触发。障碍出现并阻塞正在执行的机器人或关键通道后，系统记录被阻塞任务、位置、剩余路点和当前责任；随后识别阻塞，选择具有清障能力的救援机器人，并把“清除障碍”这一新责任正式交给它。救援机器人到达障碍处后，还必须完成接触、固定/拖移或其他登记的清障动作；发送救援消息、选定救援机器人或到达障碍旁边都不算障碍已清除。只有外部状态确认障碍离开通道、通道恢复可通行，被阻塞机器人恢复原任务并继续完成其目标后，动态救援阶段才算完成。救援机器人完成清障后可以回到原任务或接收系统重新分配的任务，但原任务的剩余义务不能丢失。

**任务检查点。** 可按 `fire_rescue` 框架记录以下任务层里程碑：`assignment_applied`（分配已生效）、`extinguisher_carried`（灭火器已抓取并保持携带）、`rescue_channel_open`（通道按钮动作和外部开启状态成立）、`obstacle_removed`（若发生障碍事件，障碍已移出且通道恢复）、`mission_success`（统一成功条件成立）。检查点由任务层在安全的环境步边界保存，不由算法自行宣称；条件在安全保存前失效时应记录为未捕获，不能用之后的空闲状态补写过去的里程碑。

**统一完成判据。** benchmark 实例应让火源侦查、现场数据采集和通道开启均有外部可核验完成事件；灭火器任务已完成且携带者到达火源附近；至少三台登记机器人处于火源半径内；若动态障碍曾触发，则障碍救援已完成且原任务已恢复。`fire_rescue` demo 当前统一成功函数重点检查救援通道、灭火器交付、必要的物理清障以及至少三台机器人到达火源邻域；数据采集完成应在最终 benchmark evaluator 中单独注册并纳入任务结果，不能因为 demo 成功函数没有该字段就默认为已完成。具体半径、数量、数据格式和“附近”阈值由实例注册。仅算法返回成功、机器人到达某个 waypoint、发送消息、到达按钮/障碍旁或灭火器曾经抓到过，都不能单独结束任务。

**回放与验收边界。** `fire_rescue` 提供原生任务检查点、物理回放和独立重建流程，可用于验证分配、搬运和清障阶段的记录一致性。回放成功只说明已登记的状态通道和有限物理窗口通过检查，不能自动证明任意算法、任意时长、所有传感器历史或隐藏的求解器状态都被完整恢复；最终 benchmark 仍需单独注册可回放的状态、输入、随机性和 evaluator 证据。

**合同候选与边界。**

| 合同候选 | 本场景的对应关系与检测目的 |
|---|---|
| C-P1-01 | 侦查、数据采集、通道开启和灭火器运输在能力、路线和时间确实独立时形成互补并行；不能仅因有四台机器人就登记并行。 |
| C-P2-01 | 动态障碍发生后，系统把清障责任交给救援机器人；被阻塞机器人恢复后继续原任务。也可记录任务分配阶段的责任转移，但必须有责任、剩余工作和接收后继续执行证据。 |
| C-P2-02 | 救援通道打开是依赖该通道的进入/运输前置；障碍移除并确认通道恢复是被阻塞机器人继续前进的前置。每次依赖动作前都要重新验证条件仍有效。 |
| C-P4-01（条件候选） | 只有登记的动态障碍确实造成通道容量竞争或阻塞，并记录进入、占用、阻塞、清除和释放时才登记排他资源；障碍物存在本身不自动构成 P4。 |

当前不登记 C-P3S-01、C-P3J-01、C-P1P2-01 或复合资源交接：本故事是一次性救援，灭火器由单个合格机器人完成，侦查/数据/按钮/运输之间没有必须齐套后再交给单一接收者的汇合义务。若未来加入持续灾情监测、双机器人共同抬运或资源资格必须先于责任接收的变体，应另行注册任务版本和合同关系。

3. **取餐与上菜：** 点单记录完成后，系统调度合格机器人到吧台取得对应餐品，核对顾客、餐桌和订单匹配关系，再把餐品送到正确餐桌并实际放下。餐品已准备好这一假设、吧台取餐面和桌面交付判据后续绑定。
4. **自主调度：** 不规定机器人数量、角色名称或具体时刻。不同顾客的引导、点单和上菜可以并行；同一顾客必须满足“就座后点单、点单记录后取餐和上菜”的依赖关系。机器人之间实际转移顾客或订单责任、已完成步骤和剩余工作时，才登记责任交接；同一机器人连续完成工作不强制拆分交接。

**合同候选与边界。** C-P1-01 对应不同顾客之间真实独立的引导、点单和上菜机会；C-P2-01 对应实际发生的顾客或订单责任接续；C-P2-02 对应就座先于点单、点单记录先于取餐上菜，以及餐桌匹配先于桌面放置。机器人数量开放不等于一定存在并行，仍须由地图、能力和多个顾客任务证明独立机会。一次性餐厅服务不登记 C-P3S-01，不加入固定服务窗口、成员退出、联合搬运或共享资源排他。

**完成判据与后续绑定。** 外部验收保留顾客到达餐桌并就座、订单记录、餐品取出、顾客/餐桌/订单匹配、餐品实际放置和订单完成事件。到达桌边、拿到餐品或发送交付消息都不能代替桌面放置。后续绑定吧台、接待区、餐桌、顾客行为、订单记录接口、已准备餐品、机器人交互/抓取/运输能力和可通行路线；不冻结机器人数量、坐标或时间阈值。

## warehouse 用户场景任务卡：仓库货物整理、清障与重物联合搬运

**完成判据与后续绑定。** 外部验收保留目标货物身份、挡路物移出、目标可达状态恢复、高层无人机取放、低层机械臂取放、重物多机器人同步搬运与稳定放置，以及每件货物到达登记目标位置的事件。到达货架、抓住货物、清障机器人到位或单个机器人短暂接触重物都不能算完成。后续绑定货架层高和可达面、货物身份/重量/抓取接口、无人机合法飞行空间与载荷能力、机械臂能力、重物联合支撑判据、挡路物临时放置区和最终目标位置；不冻结坐标、机器人数量或时间阈值。

## 第一批：三大类的任务候选示例（待按场景审定）

### A. 工厂：多工位物料齐套与配送

- 场景：`Production and logistics/factory`。
- 大类与目标：生产；为多个工位备齐所需物料并实际交付到允许接收的位置。最终评价物料、数量、目的工位及流程条件是否正确。
- 团队任务链：从不同物料区拣取互补物料 → 汇合形成工位所需套件 → 将物料及配送责任交给运输角色 → 运至工位交付。多个工位构成同一团队任务包；当前不要求模拟真实加工设备运行。
- 合同候选：单个套件的独立前置拣取与下游责任交接对应 C-P1P2-01；若装载位有真实争用和准入要求，再登记 C-P2P4-01 等实际包含的关系。拣取能否并行、交接是否确有必要须由能力配置与地图核验，不凭叙事自动认证。
- 能力：物料识别、取放装载、稳定运输和交付；合格候选可重叠，身份不预分配。
- 测量问题：能否形成可行分工；是否在齐套前错误放行；信息/责任与实际物料是否一致；替补与距离是否影响完成、进度和成本。
- 事件候选：执行者退出、交接消息退化、额外工位需求、共享装载位关闭。先单因素，不要求一次运行全发生。
- 地图需求：多个物料来源、齐套/装载区、多个工位交付面和连接区域；如测试资源合同，需要真实共享装载区域。实际物料对象与可操作面由后续绑定核验。
- common 候选：C-P1P2-01 或资源交接子任务，可与其他领域符合相同抽象条件的实例配对；目前无已认证配对。

### B. 餐厅：顾客引导、桌边点单与供餐服务

- 场景候选绑定：`Service and operations/restaurant`；不与生产组同名目录混用。
- 大类与目标：服务；让顾客从吧台到达指定餐桌，在桌边完成点单，并把对应餐品正确放到桌面。顾客、餐桌和订单必须保持一致，单纯物料送达不足以表达本大纲的全部服务义务。
- 团队任务链：吧台等待 → 顾客引导并就座 → 到桌记录点单 → 点单记录后从吧台取出已准备餐品 → 按顾客/餐桌/订单匹配并实际卸载到桌面。不同顾客的工作可以重叠；暂不加入烹饪与清洗。
- 已确认边界：订单内容需在顾客餐桌现场交互获取；到达餐桌不算点单完成，到达桌边或拿到餐品也不算上菜完成；机器人数量、角色和具体时间线均开放，由系统自主分工；不固定要求跨机器人交接。
- 合同候选：顾客就座后点单、点单记录后取餐上菜对应 C-P2-02；真实跨机器人顾客/订单责任转移对应 C-P2-01；不同顾客之间有实际独立工作机会时对应 C-P1-01。一次性服务不自动构成 P3-S，也不加入资源交接或排他约束。
- 测量问题：是否遗漏、重复或送错订单；是否能把订单状态交给正确后续成员；服务响应/等待、实际完成、接替恢复与运动成本如何变化。
- 事件候选：点单或配送成员退出、订单消息退化、追加订单；正常工作集与中途新增请求分开。
- 地图需求：接待区、吧台顾客等待区、顾客引导路线、餐品来源/取餐面、桌面交付对象、可通行区域与机器人部署区。当前只提出语义需求，不指定坐标或现有资产中必有的点位。
- common 候选：以具有可追踪责任和剩余工作状态的服务交接阶段构造 C-P2-01 配对；不能因都“搬东西”就与工厂完整任务配成同一 anchor。

### C. 家庭：为住户恢复通行并准备活动空间

- 场景：`Living and public space/house`。
- 大类与目标：生活/公共；让住户指定活动区域可用、相关通路畅通，并在允许访问的空间内备好活动用品。空间可用性及访问约束属于成功条件，不只考物品搬运数量。
- 团队任务链：获得住户授权范围及用品需求 → 清理相关通路的可移动障碍，同时在可独立访问的区域整理活动区或备好用品 → 通路条件成立后运输用品进入目标区域 → 正确放置并保持通道可用。若物理布局不支持这些独立前置工作，则调整义务图而不强行保留并行。
- 合同候选：通路清理与后续通行对应 C-P2-02，且在依赖动作执行时通路必须仍然有效；独立准备工作满足条件时对应 C-P1-01。只有真实共享狭窄通道竞争时才加 C-P4-01。当前不假设有必须共同抬起的重物，不强行加入 P3-J。
- 能力：空间/障碍识别、物体整理与操作、运输；由候选机器人池自主分工。授权只约束具体任务访问，与任意限制 Skill 翻译层不同。
- 测量问题：是否尊重访问范围；是否在前置条件不成立时通行；清理后是否再次堵塞通路；任务变更或人员退出后是否继续完成其余准备工作。
- 事件候选：清理成员退出、前置完成消息延迟、通路临时关闭；危险条件需另有安全应对机会和外部判据。
- 地图需求：活动区域、允许访问范围、待清理连接区域、用品来源/目标面和障碍合法暂存区；不默认存在房门权限控制、人类行走或重载协作等尚未认证功能。
- common 候选：C-P2-02 前置条件驱动的协作，与其他领域“先建立可用条件、再执行依赖动作”的实例配对；不进入责任交接专用分母。
