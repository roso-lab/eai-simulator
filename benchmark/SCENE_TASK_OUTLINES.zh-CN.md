## 用户观察驱动的逐场景工作流（2026-10-12，用户指定）

1. **用户提供场景与想法。** 用户说出场景名，用自然语言描述自己看到的区域、楼层、通道、物体和限制，以及想到的任务。不要求一次填完整表格、不要求先提供地图或坐标。遇到同名场景时先澄清具体目录。
2. **整理事实与未知。** 主代理简短复述与任务有关的观察，区分“用户观察”“用户任务设想”“助手推测”“待工程验证”。看得到货箱不等于已能抓取，有楼梯不等于机器人已能上下楼；未知信息不自动补成事实。
3. **围绕用户任务做 benchmark 整理。** 保留原始意图，整理三大类归属及终端目标、完整团队任务链、能力组和信息流、合同候选、可观察的完成/失败/接续证据及测量问题。用通俗语言解释为什么对应某合同；不机械套满 P1–P4 或 D1–D6。检查是否只有多个独立单机动作、交接是否必要、信息是否实际需要获取，以及是否自然形成异构协作。
4. **提出有依据的扩展。** 原始任务与扩展分开，通常提出一至三个有价值的方向，说明利用了用户描述的哪个场景特征、补充什么协作测量、还依赖什么能力。缺乏场景依据的不当作推荐任务；新增对象、技能或事件显式标注为待建设。机器人池自主调度、真实空间成本和公开信息权限沿用既定原则。
5. **只追问关键问题。** 优先用已有描述推进；确有影响任务成立或分类的缺口时，一次询问一个关键问题。用户确认的是哪一层就只记录哪一层，不能把宏观认可提升为地图/技能认证。
6. **记录并移交后续绑定。** 在本文件追加或修订该场景任务卡，保留观察来源、原始想法、已确认主任务、可选扩展和待验证事项。其他开发者完成语义地图后再选点、绑定对象/机器人、细化阈值并认证；本阶段不部署场景、不改运行 catalog、不向协作者自动发送消息。

用户输入可以很简单：“场景是……；我看到……；我想让团队完成……”。主代理每轮输出以“场景理解 → 用户任务的团队流程 → 合同/测量依据 → 可选扩展 → 必要时一个问题”为顺序，避免反复解释已确认规则。

记录状态分别为：备选素材、基于观察的提案、用户已确认任务语义、待地图/技能验证、已认证实例。已有 30 行均仍为备选素材，只有经过上述流程的具体内容才能升级状态。

## home_02 用户场景任务卡：宠物饮水与喂食准备

状态：2026-10-12 当前阶段任务大纲与双水源评价原则已确认，记录可移交后续地图/技能绑定；未完成物理实现认证、阈值冻结或 common 配对认证。已确认轻载吊运、机械臂倾倒、持碗时不能同时开门、猫粮无需开包，以及任务正确性与多维成本分别评价。用户后续明确允许先自行开门再取物，也可求助；门可能自动回关，具体条件待登记。此卡取代下方 home_02 泛化候选行，其他场景不照搬；未确认的事件扩展仍单列。

**观察与来源。** 场景身份为 `usd/scene/Living and public space/home_02`。用户截图 `/tmp/codex-clipboard-dcd4076e-f29b-4159-a326-8ff70ad6390f.png` 可见多个房间、隔墙、连接开口、卫生间样式区域及较大公共区域。用户补充：有两处距离不同的取水点，厕所洗手台较高，高货架上有猫粮，客厅有目标宠物碗，房门需要带机械臂机器人协助打开。后几项作为用户描述记录，图片本身不能认证水源可交互、门可转动、食物可抓取或液体可倾倒。

**用户原始设想。** Pepper 在高洗手台接水并交给小车运输；带机械臂成员协助开门；最终倒入客厅宠物水碗。无人机从高货架取猫粮、放到小车上，再运到猫粮盆倾倒。

**类别与团队终端目标（建议）。** Living/public：在家庭访问与安全约束下，使宠物能够在指定位置获得适量饮水和食物，保持相关通路和使用区域可用。两个补给分支共同满足生活照料目标，不以“容器送达”代替完成，不要求模拟宠物进食。若实例最后仅保留货物运输而去掉生活可用性目标，需重新核对领域归类。

**两条任务链。** 饮水：选择可用取水点与合格成员 → 获取/使用合适接水容器 → 接水 → 合法装载与配送责任交接 → 在相关房门已可通行时运输 → 由机械臂在目标水碗完成倒水。食物：定位/核验猫粮 → 具备轻载吊运能力的无人机取下猫粮 → 稳定放置并交接给运输成员 → 经必要开门协助送到喂食区域 → 由机械臂将食物倒入目标食盆。用户明确猫粮无需开包，不添加开包义务。开门是所影响路径的前置条件，不强行给两条链都增加无实际作用的开门步骤；分支间真实资源竞争单独记录。

**机器人和能力边界。** 用户指定默认无人机具备吊运轻型资产的能力，此能力应写入对应实例简历，后续核验载荷范围与实现，不再作为宏观任务是否可选的悬而未决项。倾倒由机械臂完成，小车承担运输；猫粮按可直接倾倒的任务物料处理，不设计包装开启。高洗手台仍需合格机械臂的可达性、抓持及取水接口。高度本身不证明只有无人机能完成；其他真实合格候选仍按池规则调度。

**持碗与开门的执行约束（用户确认并补充）。** 机械臂持碗时操作能力被占用，不能同时开门；若此时门关闭且没有合法可用的自助操作方式，需要另一名具备开门能力的成员协助。用户明确允许先自己打开门，再进去取物并出来；不能将调用另一台机器人设为所有执行的成功条件。门可能自动回关，历史开门记录不保证当前可通行。该约束只绑定实际持碗区间与所用操作资源，不是机器人永久禁止开门，也不是一律要求开门者必须用不同型号。若要放下容器后自行开门，必须有合法放置面、物理状态变化和拾取代价；是否允许该替代方案须后续登记，不能靠释放软件锁让容器凭空悬置。持碗与运输载具的具体装卸边界后续据地图/技能落实，不强制增加没有实际作用的交接。

**合同与测量候选。**

- C-P1-01：水与食物均为必要贡献；只有能力和资源配置确有并行机会时才登记并行关系，共享一台运输车造成部分串行需在完整图中保留。
- C-P2-01：取水/取粮后移交物品、目标及残余工作给运输或倾倒成员。仅物体接触或同一机器人继续工作不能伪造跨成员责任交接。
- C-P2-02：开门使后续通行可行，通行时门的状态须仍有效。是否开门后保持开启，或必须持续扶门，尚待用户/地图确认；后者需要另审持续服务窗口，不能自动叫作联合搬运。
- C-P4-01：仅在多个真实任务竞争同一门口、装载位或操作区且有合法容量约束时适用。门窄、门关闭或需要机械臂本身不足以成立排他。
- 全任务首先是典型家庭任务；common 候选可来自前置或交接阶段，但不把两分支并行自动等同于 C-P1P2-01，除非确有汇合后的必要责任交接。

规划测量关注能否选出合格机器人、水源与工作安排；关系测量关注门状态、真实交接与残余任务接续；终端证据关注目标碗中实际可用的水/食物量及注册的溢出、错盆等条件。水源距离通过真实路径、速度、门操作、等待和倾倒等影响进度与成本，不能直接以“选最近水源”判成功。事件扩展后按既定 D2/D4 规则建面板，D5 仍需跨域配对认证，D6 不新增未经审定的混合总分。

## house 用户场景任务卡：庭院用餐与阅读准备

状态：2026-10-12 用户认可宏观方向，并补充桌子可采用双机器人搬运、椅子由单机器人搬运。记录为包含联合搬桌的任务大纲；具体目标桌、物理参数、门行为条件及地图/技能认证仍待落实。替代下方 house 泛化行作为当前讨论入口，未确认的事件扩展仍单列。

**共同目标（建议）。** 归 Living/public：把住户指定的室内相关区域整理到要求状态，并准备好庭院用餐/阅读区域，使桌椅和通路可用，指定水果及书籍实际放到可取用位置。明确哪些整理工作是住户独立要求、哪些是为后续取放/通行建立前置条件，不能随意安排无关家具移动只为增加机器人数量。

**任务分支。** ① 空间整理：按公开目标状态调整指定桌椅/物品，保留出入口与必要通路，准备庭院目标放置面。② 水果：厨房选取指定水果或轻载容器 → 由已设定具备轻载吊运能力的无人机获取/接收 → 沿实际可飞、可出入的路线运到庭院 → 稳定放在指定桌面，或交给合格接收成员完成摆放。是否需额外成员装载由吊点/容器与技能决定，不自动增加。③ 书籍：从书架获取指定书籍 → 自行跨越合格路径或交给具备台阶通行能力的成员 → 经当前可通行的门送到庭院 → 放入指定阅读位置。不得只以无人机悬停或机器人到达室外判交付完成。

**桌椅搬运（用户补充确认）。** 在需要调整桌子位置的整理任务中加入双机器人联合搬桌；椅子由一个具备相应能力的机器人搬运。桌子绑定为需要两个合格参与者共同支撑与协调移动的对象，具体重量、尺寸、抓持位置及单体能力约束后续验证，不能仅凭外观宣称物理必需。由被测系统从机器人池选择两名参与者，不固定型号/身份；两者就位并建立合法支撑后，在注册同步窗口与联合状态约束内搬运，最后稳定放置并解除支撑。轮流搬、一个搬另一个旁观不能算联合完成。椅子允许单体完成，不要求另一成员陪同，也不因两台机器人分别搬两把椅子就登记 P3-J。

**流程关系。** 分支准备在真实能力与资源允许时可以并行。两名成员搬桌时占用相应操作资源，其他合格成员可搬椅、取书或准备水果；不能让同一机械臂在支撑桌子的同时开门或执行其他不兼容工作。若这张桌子是水果/书籍的最终放置目标，先稳定就位再允许最终摆放，提前取物和运输到合法等待点仍允许；不假设所有物品都必须放在该桌上。若桌面或通路需要整理，最终摆放/通行等待对应条件成立，不强行要求整个整理分支完成后所有运输才启动。台阶产生载荷状态下的可达性要求，与门的开闭条件分开检查。无人机在室内外如何转接、物体形态和目标承载面待地图/技能绑定，不假设飞行能绕过所有门。

**门的时变前置条件（同样修正 home_02）。** 用户允许先开门后取物、也允许呼叫其他成员开门。合同要求实际通行期间满足所需净空与安全条件，而非要求调用某个助手或保留历史“开门完成”标志。门若自动回关，需要重新确认、重新开门、安排协助或采取其他允许的合法策略。建议将“开启后保持”和“注册规则下自动回关”作为可分辨条件；关闭触发、延迟、可见信息与安全应对机会后续登记，不能事后任意关门制造失败。普通门回关不自动构成成员重配置 D4 主面板或 P4 资源冲突。

## 设计原则更新：宏观主题由类别引导，任务由具体场景支持

2026-10-12 用户明确：不能将工厂一概设计成物料配送。有些工厂具有二楼、楼梯，可考虑巡视与应急响应；储存仓可考虑货箱查找与搬运。三大类用于制定宏观主题，具体任务依实际结构、对象及机器人可执行能力设计。以下首批大纲保留为候选，不视为同类场景的统一模板或已确认的唯一任务。

当前流程为：类别主题 → 已知场景特征及待核验项 → 若干团队任务候选 → 合同和测量对应 → 语义地图就绪后的选点与布置。可以在地图完成前提出带条件的候选，不把楼梯、操作对象等假设写成已核实资产事实，也不要求地图开发者按既定故事虚构布局。

类别有两层用途：场景宏观主题可以是“工厂生产与安全运行”，其中包含多种工作；正式可评分实例仍按论文的最终目标登记唯一 domain。例行巡视若只作为生产放行的前置阶段，可属于生产任务链；若整项任务以持续运营、异常响应和责任接续为目标，应审查 service 归类。应急响应也不能仅因发生在工厂就固定归 production。跨类候选明确标记，后续核对三类覆盖，不为了凑数量或沿用目录位置更改语义。

每个场景的大纲增加“已知特征/信息来源、待地图确认条件、可替换任务候选”三项。当前只记用户指出某些工厂可能具有二楼楼梯，不据此断言 factory 或 factory_02 的实际结构。

## 地图开发者的最小反馈（需求清单，不是新增地图实现）

逐场景提供现有事实即可：楼层/地形与连接关系；可通行区域及按机器人形态区分的限制；可观察目标和可操作物体；交互/放置表面；可作为真实共享资源的区域；权限/危险边界；尚缺或不确定的内容。我们再选择适合的候选任务。哪些信息开局公开、需要现场发现或属于 evaluator-only，应在任务侧另行声明；地图包含真值不等于模型可以读取全部真值。

本轮优先审定宏观主题及候选方向，后续按三类逐批审查任务是否自然、是否团队级、是否真的测到所列合同。确认后才做任务实例、机器人配置、地图绑定及物理指标细化，不修改旧运行 catalog 来伪装已经落地。

## 第一批：三大类的任务候选示例（待按场景审定）

### A. 工厂：多工位物料齐套与配送

- 场景：`Production and logistics/factory`。
- 大类与目标：生产；为多个工位备齐所需物料并实际交付到允许接收的位置。最终评价物料、数量、目的工位及流程条件是否正确。
- 团队任务链：从不同物料区拣取互补物料 → 汇合形成工位所需套件 → 将物料及配送责任交给运输角色 → 运至工位交付。多个工位构成同一团队任务包；当前不要求模拟真实加工设备运行。
- 合同候选：单个套件的独立前置拣取与下游责任交接对应 C-P1P2-01；若装载位有真实争用和准入要求，再登记 C-P2P4-01 等实际包含的关系。拣取能否并行、交接是否确有必要须由能力配置与地图核验，不凭叙事自动认证。
- 能力：物料识别、取放装载、稳定运输和交付；合格候选可重叠，身份不预分配。
- 测量问题：能否形成可行分工；是否在齐套前错误放行；信息/责任与实际物料是否一致；替补与距离是否影响完成、进度和成本。
- 事件候选：执行者退出、交接消息退化、额外工位需求、共享装载位关闭。先单因素，不要求一次运行全发生。
- 地图需求：多个物料来源、齐套/装载区、多个工位交付面和连接区域；如测试资源合同，需要真实共享装载区域。实际物料对象与可操作面由后续绑定核验。
- common 候选：C-P1P2-01 或资源交接子任务，可与其他领域符合相同抽象条件的实例配对；目前无已认证配对。

### B. 餐厅：多桌顾客的点单与供餐服务

- 场景候选绑定：`Service and operations/restaurant`；不与生产组同名目录混用。
- 大类与目标：服务；多个顾客请求有明确责任、得到响应并完成正确交付，任务暂停或人员变化不能使已有订单丢失。单纯物料送达不足以表达本大纲的全部服务义务。
- 团队任务链：现场获取订单 → 按单选取并装盘已有餐品 → 装载和配送责任交接 → 运输 → 具备操作能力的成员实际卸载到指定桌面。跨桌工作可重叠；暂不加入烹饪与清洗。
- 已确认边界：订单内容需现场交互获取；到达桌边不算交付；使用带简历的多候选机器人池；正常配置能力部分重叠、有有限冗余且位置分散。桌数、餐品组合仍未冻结。
- 合同候选：点单后按单备餐对应 C-P2-02；真实跨机器人订单/配送责任转移对应 C-P2-01；资源交接在条件成立时可用 C-P2P4-01。单份订单的点单与按单备餐不能硬记为并行。服务类别或长时运行本身不构成 P3-S，需要明确持续服务义务时再审定相应合同。
- 测量问题：是否遗漏、重复或送错订单；是否能把订单状态交给正确后续成员；服务响应/等待、实际完成、接替恢复与运动成本如何变化。
- 事件候选：点单或配送成员退出、订单消息退化、追加订单；正常工作集与中途新增请求分开。
- 地图需求：顾客交互区域、餐品来源、装盘/装载区域、桌面交付对象、可通行区域与机器人部署区。当前只提出语义需求，不指定坐标或现有资产中必有的点位。
- common 候选：以具有可追踪责任和剩余工作状态的服务交接阶段构造 C-P2-01 配对；不能因都“搬东西”就与工厂完整任务配成同一 anchor。

### C. 家庭：为住户恢复通行并准备活动空间

- 场景：`Living and public space/house`。
- 大类与目标：生活/公共；让住户指定活动区域可用、相关通路畅通，并在允许访问的空间内备好活动用品。空间可用性及访问约束属于成功条件，不只考物品搬运数量。
- 团队任务链：获得住户授权范围及用品需求 → 清理相关通路的可移动障碍，同时在可独立访问的区域整理活动区或备好用品 → 通路条件成立后运输用品进入目标区域 → 正确放置并保持通道可用。若物理布局不支持这些独立前置工作，则调整义务图而不强行保留并行。
- 合同候选：通路清理与后续通行对应 C-P2-02，且在依赖动作执行时通路必须仍然有效；独立准备工作满足条件时对应 C-P1-01。只有真实共享狭窄通道竞争时才加 C-P4-01。当前不假设有必须共同抬起的重物，不强行加入 P3-J。
- 能力：空间/障碍识别、物体整理与操作、运输；由候选机器人池自主分工。授权只约束具体任务访问，与任意限制 Skill 翻译层不同。
- 测量问题：是否尊重访问范围；是否在前置条件不成立时通行；清理后是否再次堵塞通路；任务变更或人员退出后是否继续完成其余准备工作。
- 事件候选：清理成员退出、前置完成消息延迟、通路临时关闭；危险条件需另有安全应对机会和外部判据。
- 地图需求：活动区域、允许访问范围、待清理连接区域、用品来源/目标面和障碍合法暂存区；不默认存在房门权限控制、人类行走或重载协作等尚未认证功能。
- common 候选：C-P2-02 前置条件驱动的协作，与其他领域“先建立可用条件、再执行依赖动作”的实例配对；不进入责任交接专用分母。
