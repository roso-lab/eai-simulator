# Benchmark 任务生成与审核阶段进展及协作对齐

日期：2026-09-17

## 汇报目的

本阶段工作的目标，是建立一套能够持续产出有场景意义、可执行、可审核、可评价的异构多机器人任务体系，并把任务生成与场景资产、机器人运行时、被测 agent、因子实验和评价模块连接起来。

当前已经形成 Factory、Warehouse NVD、Modern House NVD 三类业务任务骨架，以及统一的公开题面、参与者接口、隐藏评价和发布审核边界。三类任务已可以支持受约束的 LLM 任务实例生成和后续模块联调。Warehouse 和 Modern House 已完成运动学参考流程验证；完整 benchmark 仍需补齐实时业务证据、物理参考执行、动态团队变化和楼梯实爬等关键证据，因此当前不应宣称已经可以正式计分发布。

## 一、任务生成在整体 Benchmark 中的位置

任务生成不是单独编写一段机器人动作脚本，而是把“希望评价的能力”转化为其他模块都能共同理解和执行的实验契约。

整体链路如下：

```text
场景与业务目标
  + 场景资产和空间约束
  + 机器人团队与公开能力
  + 通信、成员变化等实验因子
                ↓
        场景化任务骨架
                ↓
      生成任务实例并完成审核
                ↓
  公开题面 + 参与者接口 + 隐藏评价条件
                ↓
       被测 agent 作出团队决策
                ↓
   运行时执行并记录动作、事件和环境证据
                ↓
        评价模型评分并进行失败归因
```

在这条链路中，任务生成侧负责定义“要完成什么、为什么有意义、允许使用哪些资源、需要留下哪些证据”；运行时负责让这些条件真实发生并记录；被测 agent 负责在可见信息下完成分配、协作和恢复决策；评价侧根据隐藏真值和运行证据判断结果。

## 二、当前已经形成的三类任务规划

三个场景不再共用“搬运加探查”的通用模板。扫描、导航、搬运和等待只是完成业务目标的手段，每个场景都有自己的对象、流程、验收条件和协作理由。

| 场景 | 业务任务主线 | 异构协作重点 | 任务成功的实际含义 |
| --- | --- | --- | --- |
| Factory | 根据空中和地面证据完成生产异常确认与工位派遣 | 无人机先取得全局证据，地面机器人近距离复核，不同通行能力影响可达区域 | 派遣结果与证据一致，目标工位选择正确，关键路线可达 |
| Warehouse NVD | 完成指定订单的货架识别、集货、出库交接和库存复核 | 空中盘点、地面取货、大件联合搬运、dock 交接和通信变化后的改派 | 正确物品以正确顺序进入出库链，身份和交接证据连续 |
| Modern House NVD | 在住户回家前恢复家具布置和生活通行路径 | 空中观察、双侧家具作业、联合移动、物品暂存和最终净空复核 | 家具和物品处于合理位置，入口及生活动线真正恢复 |

Factory 的楼梯入口 `F-VERT-01` 已作为独立能力诊断任务保留并向题面开放。楼梯不是装饰性障碍，而是用于体现不同机器人形态和通行能力差异的关键条件。当前仍需完成踏步测量、机器人支撑与控制校准、参考轨迹和真实爬楼证据，完成后才能把它纳入正式可计分任务。

Warehouse 使用木箱、纸箱、货架和 dock 等仓储对象；Modern House 使用扶手椅、书堆和入口通路等家居对象。任务对象和动作含义均来自场景常识，避免为了构造协作而加入与场景无关的障碍或道具。

## 三、任务生成侧的输入与交付

任务生成侧需要接收四类上游信息：

1. 场景团队提供稳定的场景版本、对象身份、空间区域、可通行路线和业务语义。
2. 机器人与运行时团队提供机器人能力、传感器、控制接口、联合操作语义以及可记录的执行证据。
3. 因子实验团队提供要比较的通信、团队成员和能力变化条件，以及各条件的冻结范围。
4. 评价团队提供最终需要判断的业务结果、失败类型和证据要求。

任务生成侧据此向 benchmark 其他部分交付一组配套材料：

| 交付内容 | 主要使用方 | 作用 |
| --- | --- | --- |
| 场景任务实例 | 场景编译器、运行时 | 固定本次实验的对象、目标、团队、子任务关系和约束 |
| 公开任务说明 `public_task.json` | 被测 agent、baseline、展示层 | 告诉 agent 当前目标、团队能力、任务节点和公开规则 |
| 参与者接口 `participant_api.json` | agent 接入层、运行时 | 约定 agent 可以提交的分配、改派、行动和消息操作 |
| 因子说明 | 实验编排与统计模块 | 声明本次改变什么条件、哪些条件必须保持一致 |
| 隐藏评价条件 `hidden_evaluator.json` | evaluator | 保存对象真值、业务验收条件、事件计划和评分证据 |
| 审核与发布状态 | benchmark 管理和 QA | 明确任务是否仅可联调、是否完成执行验证、是否可以计分 |

这些材料共同保证公开题面、执行接口和隐藏评分彼此一致，同时避免把答案或未来干预提前暴露给被测 agent。

## 四、被测 Agent 实际接收和输出什么

当前主 track 采用“业务目标加固定任务骨架”的形式。被测 agent 会得到：

- 场景和业务目标；
- 本轮机器人团队及其公开能力；
- 子任务、对象、依赖关系和完成规则；
- 当前可使用的动作与通信接口；
- 截至当前时刻已经公开的观察、通信和团队事件；
- 当前实验因子的名称和公开规则。

被测 agent 不会得到隐藏对象真值、未来成员退出时间、未来通信干预、参考分配方案或 evaluator 的私有验收条件。

agent 输出的是可执行的团队决策，包括任务分配与改派、导航或作业请求、联合任务参与关系、等待与恢复选择，以及对已到达消息的消费。运行时把这些决策转化为机器人执行，并产出位置、观察、对象状态、通信、团队变化和任务完成证据。最终成功由 evaluator 根据证据判断，不能由 agent 自行声明。

固定骨架的目的，是先稳定比较模型在团队分工、异构能力利用、信息使用和扰动恢复方面的能力。后续可以增设“自主任务分解”track，只给业务目标和可用原语，让模型自己生成子任务和依赖；该 track 需要独立的任务合法性审核和更强的隐藏验收器，不应与当前结果直接混合比较。

## 五、任务审核分为四步

审核关注的是题目是否成立以及结果是否可解释，而不是开发过程本身。

### 1. 场景与业务审核

确认任务目标符合工厂、仓库或家居场景的真实需求；对象、动作和成功条件之间存在业务联系；异构团队的加入确实带来能力互补，而不是人为增加机器人数量。

### 2. 可执行性与公平性审核

确认场景中存在所需对象和路线，机器人能力能够覆盖任务要求，联合任务具备明确的参与和结束条件，所有对比组使用一致的场景、对象、预算和任务目标。无人机简易避障、地面导航和动作合法性属于基础执行条件，不计作异构协作成绩。

### 3. 信息与因子审核

确认 agent 只能使用当时可见的信息，未来通信和团队事件不泄露；单因子实验只改变一个主要条件；消息延迟、成员退出和能力变化确实发生在能够影响决策的时间窗口内。

### 4. 证据与发布审核

确认每个成功条件都能由运行证据支持，失败能够定位到具体阶段，参考流程可以重复执行。缺少实时业务证据、物理执行或关键因子对照时，任务可以用于联调和协议审核，但不能进入正式计分集。

## 六、协作行为与基础设施的职责边界

任务设计必须把“平台应保证什么”和“被测算法应决定什么”分开，否则评价结果无法解释。

基础设施需要提供：

- 机器人加入、退出和能力变化的事件语义与证据；
- 通信延迟、丢包、过期和消息消费记录；
- 联合搬运的共同接取、共同持有、队形距离和共同释放语义；
- 无人机基础避障、地面合法通行、对象身份和场景状态证据；
- 任务节点从开始到验收的统一事件记录。

被测算法需要决定：

- 哪些机器人适合承担当前子任务；
- 快车是否等待慢车、在哪里会合以及何时开始联合动作；
- 成员退出、能力下降或通信变化后如何重新分配；
- 哪些观察和消息值得使用，过期信息是否应被放弃；
- 如何在完成业务目标的同时控制时间、资源和协作成本。

因此，“快车等慢车”本身是 agent 的协作策略；但系统必须提供可靠的会合、等待、共同持有和释放机制，并记录这些动作是否真实发生。只有两侧同时成立，评价模块才能把算法决策问题和底层执行问题区分开。

## 七、子任务设计如何支持因子溯因和评价

子任务点的价值不在于增加步骤，而在于建立一条可以追踪的业务证据链。

| 证据阶段 | 评价要回答的问题 | 可归因的失败 |
| --- | --- | --- |
| 观察与信息获取 | agent 是否获得并使用了必要证据 | 漏检、错误观察、未消费消息、使用过期信息 |
| 分配与团队形成 | 任务是否交给具备能力的成员 | 能力匹配错误、联合成员不足、退出后未改派 |
| 运动与作业执行 | 机器人是否到达并合法完成动作 | 路线失败、碰撞、联合持有或释放失败 |
| 业务交接 | 对象身份和服务状态是否连续 | 送错物品、dock 未接收、家具位置不满足要求 |
| 最终复核 | 环境是否达到真正目标状态 | 工位选错、库存不一致、生活通路仍被阻挡 |

在因子实验中，同一任务需要保持布局、对象、机器人能力、时间预算和模型预算不变，只改变一个主要条件。例如比较通信延迟时，应观察任务完成率、关键信息使用、恢复时间、改派次数和最终业务结果如何变化；比较成员退出时，应观察 agent 是否识别团队变化、停止无效计划并建立新的可执行分配。

这种设计让最终评分不只给出“成功或失败”，还可以回答失败发生在基础运动、协作协议、信息使用、团队恢复还是业务验收，并为后续因果分析提供成对、可比较的运行证据。

## 八、当前成果与仍需联动完成的工作

当前已经完成的阶段成果包括：

- 三个场景均形成了与场景业务紧密相关的任务主线和可扩展骨架；
- 公开题面、agent 接口、隐藏评价和发布状态的边界已经统一；
- 联合搬运、通信和团队变化具备可审核的协议语义；
- Warehouse 和 Modern House 的运动学参考流程已完成，地面路线、无人机路线、相机窗口、联合搬运和运行状态检查均有通过记录；
- 相关任务契约、执行组件和审核规则已通过聚焦回归检查。

下一阶段需要各模块共同闭环以下事项：

| 协作方 | 需要共同完成的事项 | 完成后支持的能力 |
| --- | --- | --- |
| 场景与资产团队 | 冻结场景版本、对象身份和关键空间区域 | 保证任务实例和评价真值稳定可复现 |
| 运行时与机器人团队 | 接入真实对象、dock、通路证据；补联合搬运和家具操作物理参考执行 | 从运动学流程提升为可验证的物理任务 |
| 动态团队与通信模块 | 完成真实成员加入、退出、能力变化和有效决策窗口内的成对重放 | 支持团队韧性和通信因子的正式比较 |
| Factory 场景团队 | 完成楼梯测量、控制校准、参考轨迹和实爬验证 | 将关键异构通行能力纳入可计分任务 |
| Agent 接入团队 | 按公开题面和 participant API 接收任务并输出结构化决策 | 形成统一、可替换的被测 agent 接口 |
| 评价与统计团队 | 确认业务成功、恢复能力、协作合法性和资源成本的指标聚合方式 | 输出可解释的总分、分项分和因子效应 |

## 九、本阶段希望达成的团队共识

当前交付的核心不是更多任务数量，而是一套可以共同扩展的出题框架：每道题都要有明确业务目标、合理的异构协作需求、公开和隐藏信息边界、可执行接口、可追踪证据以及可归因的评价结果。

近期应优先完成三场景现有任务的证据闭环和跨模块联调。在这些任务达到可重复、可评价、可做单因子对照之后，再基于同一骨架生成更多对象组合、团队配置和扰动实例。这样新增任务才能扩大 benchmark 覆盖面，而不会稀释任务含义或引入无法解释的分数变化。
