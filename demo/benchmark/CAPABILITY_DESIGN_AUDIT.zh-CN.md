# 五场景六能力轴任务设计审查

审查日期：2026-09-23。源码基线：`3ca55dc`；审查分支：
`codex/benchmark-capability-design-audit`。这是高层任务设计审查，
不修改冻结题包、见证计划、评分或 `scoreable=false`。

**结论：现有任务能为分配调度、顺序依赖和部分联盟协作提供题目基础，
但尚不能支持六轴完整能力成绩单。规模响应、经验学习、持续主动配合是明确缺口；
通信适应与失效恢复有契约基础，仍缺正式运行中的有效干预与模型响应证据；
成本效率只有部分原始事实。餐厅的异构互补尤其不足。**

本报告采用用户最新的能力分类。能力轴描述系统能力；机制模板、干预探针、
业务成功率与资源统计各有用途，不能相互替代。当前失败不自动表示被测模型能力不足。

## 1. 分类、轨道和证据口径

| 轴名 | 英文对照 | 在本 benchmark 中必须回答的问题 |
| --- | --- | --- |
| 分配调度 | Task Allocation & Scheduling | 在公开能力、位置、资源和任务要求下，谁做什么、何时做？ |
| 通信适应 | Communication Adaptation | 信息延迟、缺失或过期时，是否仍能作出合理协作决定？ |
| 耦合协调 | Task-Coupling Coordination | 对象交接、先后依赖、互斥和需要持续重叠的辅助任务能否正确衔接？ |
| 动态重构 | Dynamic Restructuring | 执行中的任务规模、团队或可用能力突变后，能否在线检测和重构？ |
| 动态重构—规模响应 | Scale Response | 新增任务或可用资源后，能否有效处理新增负荷或机会？ |
| 动态重构—失效恢复 | Failure Recovery | 成员或能力损失后，能否保住已完成进展并恢复可行计划？ |
| 经验学习 | Cross-Episode Learning | 在控制回合难度和预算后，前序经验是否改善后续同族任务？ |
| 成本效率 | Cost-Efficient Coordination | 在满足约束并取得有效进展的前提下，是否节制征用资源及高层交互？ |

动态重构两个子类分别测试、分别计分；不把二者合并成一个不透明的恢复数值。
安全、本体能耗、低层步数和通信字节保留为约束或横向代价，不因已有这些数值
就宣称已测成本效率。异构互补是各轴的测试条件，不另设轴。

必须分开三个对象：

1. **Goal 主轨题面**：公开业务结果、能力和约束，模型可选团队、自建计划及重规划。
2. **固定 DAG 诊断轨道**：作者固定分解，主要检查协议和执行。历史 S13 文档属于这一范围，
   不能据此断言当前 Goal 模型不能自行分解。
3. **原生 episode/适配器**：实际交给模型多少决定权，以该入口为准。
   `HouseWitnessParticipant` 播放见证；餐厅算法入口把三个预定义 mission 的分配
   交给算法，再由共用代码展开步骤。二者均不能证明通用自主分解。

覆盖证据依次是：业务需求和决策空间 → 可执行测试及干预 → 可信事件与结果 →
配对实验与统计。下表只审查前两层是否具备基础，不给模型打分，不将缺测记成零分。

## 3. 影响测量效度的具体发现

### D1：机制标签尚不足以产生不同能力挑战（P0）

`goal_driven_tasks.py::_apply_mechanism_template` 修改 ID、context 和约束描述；
`_apply_mechanism_probe_to_witnesses` 在每个 witness **最后**添加
`relay(message_kind=benchmark_mechanism:...)`。本次实际生成并比较四场景各八模板：
同一场景的 `required_outcomes`、`public_world` 和 `hidden_event_schedule` 全部相同，
末尾 probe skill 全部为 `relay`。

这能保留不同研究标签的证据入口，不能证明任务真的诱发同步、争用或恢复；
末尾 marker 也不能解释此前决策为何失败。模板中的 I-timing 描述不等于运行已施加
时间干预。公开 `business_constraints` 还直接含机制英文名，与“机制只在隐藏侧”
的代码注释不一致；应决定哪些规则需要公开，避免用能力标签给模型提示答案。

应保留现有模板为作者元数据；新版本逐个补具体依赖、干预窗口和最小反例，
不能以不同哈希或不同 relay 字符串升级覆盖结论。

### D2：串行执行限制调度与持续主动配合的可测范围（P0）

`_plan` 给作者见证逐步安排串行区间；这只是非最优参考，不应限制模型。
但 `FormalGoalEpisodeRunner.run` 也同步执行 `pending[0]` 到终态，再调用下一步。
当前入口无法凭“计划允许并发”证明两个独立技能实际重叠，也无法在阻塞技能中途
向模型交付事件并让其响应。合法并行计划可能受该后端额外串行化限制。

`cooperative_carry` 可以由一个原子技能控制多个成员，它能测试联盟成员选择和开始条件；
这不等于模型自行维持跨技能辅助服务、控制同步细节或在线接替。
`synchronize` 名称、DAG 前驱和两个任务分别成功也不能替代重叠时窗的实测。

短期明确串行参考执行的范围；正式耦合题需同一场景时钟上的可推进任务/持续服务接口。
可以使用确定性的理想技能，不需要引入高保真抓取或关节控制。

### D3：餐厅的多机收益与异构互补不足（P0）

业务是两处地面支撑/可达检查加汇总，单 Carter 串行 witness 已合法，
因此多机和异构均不能当作完成业务的必要条件。它可成为“少征用资源”的校准题，
但不能因候选池含无人机就宣称测到异构主动配合。

算法入口只保留两台 Carter 和一台 Iris；其 `MISSIONS` 与计划展开由适配器固定，
TeamWeaver 使用 catalog decomposer，EMOS 使用声明的确定性 assignment policy。
当前证据适用于该分配器/策略配置，不能扩展为完整模型推理或自由任务分解表现。
其他作者候选因未有原生准入被排除，是必须披露的执行覆盖限制，不能当算法主动舍弃。

另有已核实的接口不一致：共享题包和 `_algorithm_public_task` 派生题包都声明
`restaurant_staging.access_modes=[ground_navigation, aerial_navigation]`，
但 `MISSION_REQUIREMENTS` 对汇总 relay 额外要求 ground，`_expand_mission_plan`
拒绝空中执行者，运行只为地面成员创建 navigator。代码注释所说的“staging 仅地面可达”
与实际公开契约不符。**这是适配器的执行覆盖限制，不能解释成模型选择 Iris 违反公开规则。**
共享验证器也明确把能力/物理适配留到执行层。下一版本必须对齐公开承诺与执行接口；
未实现 aerial driver 不等于该方案已被证明业务上不可行。

餐厅任务文字允许多机并行，但正式 runner 串行执行；若直接用这个耗时比较单/多机策略，
会压低多机价值。修复方向是提供真实并行执行或明确该批结果只比较串行分配，
不能要求模型按见证的串行顺序才算正确。

### D4：成员加入不等于规模响应完整测试（P0）

`_team_treatment` 有 `member_join/member_exit/capability_change`，默认窗口在
首次跨形态观察与首次业务提交之间；`expanded_v1` 是**初始静态扩池**。
当前没有正式 Goal 新订单/新事故/新整理目标的在线发布与验收协议。
因此扩大初始候选池可测分配搜索或静态规模表现，不能替代在线规模响应。

新增资源也不必强迫改派：当前计划足够时保持原计划可能是合理答案。
应区分“新增任务导致必要重构”和“新增资源提供可利用机会”，分别设置对照与结果。
加入不与退出合并计分，不以 replan 次数多自动判好。
新任务应通过预先冻结规则的版本化事件接口发布，干预流由评测器持有，
不能运行中改写既有任务的成功标准来制造规模响应或挽救失败。

### D5：失效恢复有协议，缺保持进展的完整实验（P0）

`GoalSession.emit` 会更新当前成员/能力、标记受影响 pending、要求新快照；
这支持恢复协议，但不证明每个正式 episode 已在相关决策前实际注入事件。
退出唯一必要能力后应先检查是否仍可解；不可解时允许报告无法完成或降级的独立题型。
不能移除最后承载者、让对象状态丢失，然后按原完成要求处罚模型。

恢复题应测事件可见时间、检测/重规划、未完成职责空窗、合法接管、对象身份连续和
最终进展；退出、能力降低、队伍加入分别归档。失败不能只靠重新从初始状态跑一遍挽救。
物理技能/接近适配器的错误属于基础设施记录，不能用来合成模型恢复能力排名。

### D6：经验学习缺少跨回合实验单位（P1）

当前 Goal 生成器、host 与 runner 以单 episode 为单位；本次检索未发现完整的
历史可见范围、持久记忆/重置策略、训练—留出划分或顺序对照协议。
重复跑 seed 或同一个 witness 不构成经验学习证据。

先用同族任务的受控历史试验：同一版本系统分别使用无历史、相关历史和等预算无关历史；
冻结可见日志/反馈、可保留状态、额外推理预算与新任务难度。测试新布局/身份组合，
防止直接记住答案。用每个序列的增益和迁移结果比较，序列是独立统计单位，
不能把相邻回合当独立样本。允许模型选择不用历史；不强制某种学习或记忆实现。

### D7：成本效率目前只有部分代理量（P0）

`team_usage_summary` 已区分 selected、plan-assigned 和 dispatched 成员，记录
`action_count`；`activation_cost_proxy` 是曾派遣成员集合上的类型权重和。
它不是机器人占用时长、可撤销资源租用费用或本体能耗，不能直接解释成完整资源征用成本。
重规划、被拒请求、重复消费、按需遥测及跨接口通信也需要明确的事件口径。

先同时报告业务进展、完成时间和成本向量，在相同成功/进展门槛下比较；
无动作、未完成或拖延不能凭成本低获胜。预注册权重或报告 Pareto 比较，
不要事后用一个加权总分掩盖失败。算法进程内部通信不可观测，须记未覆盖，不能记零。

### D8：通信工具选择权与干预机会必须同时保留（P0）

用户已确定位置是工具接口：模型可不接入、按需查询或间隔订阅；不得强制订阅，
不得把不消费位置本身判错。订阅后的真实采样、投递、TTL 与字节入账需要走可信链路；
初始坐标先验、已收到的旧值与新采样须区分。

应记录每个实验是否真的在相关决策前产生了受影响消息；若模型没有使用位置工具，
该次位置 treatment 可能没有暴露机会，不能自动得出“抗通信干扰”。
也不能为了保证 treatment 命中，向不订阅的模型暗中推送坐标。
另用业务自然需要的信息设计通信题，容许合法替代信息、等待或不确定性处理。
对全丢包造成不可解的条件单列可解性，不要求猜隐藏答案。

## 4. 每场景最小有效增补方案（设计建议，尚未实施）

优先补少量能区分行为的题，不要求五个场景机械复制六套题。
同一能力可跨场景验证泛化，但每个场景应有明确主测轴和异构依赖表。

| 场景 | 保留的自然业务 | 最小增补及主动配合 | 反例/对照 |
| --- | --- | --- | --- |
| 工厂 | 异常核实与维护交接 | 可选择由高处持续观察为地面核实提供更新；资源加入或楼梯能力退出后重新分工。持续观察仅在真实遮挡/业务需要下加入 | 一次观察足够的静态对照；观察提前停止后业务事实是否缺失；不能所有视角都提供相同完整答案 |
| 仓库 | 同订单两货物交付、承载与 dock 交接 | 执行中新订单；不同载荷能力可选单机/联盟；共享 dock 争用及持货成员失效后的安全接管 | 单机可行轻载、多人必要重载、冗余成员；载荷由公开实验声明决定，不以抓取难度造协作门槛 |
| 房屋 | 整理并恢复住户通路 | 新增整理请求；分区作业的互斥与撤离顺序；若需要观察助手，给出在伙伴作业窗口内必须保持的具体可见性条件 | 最后机器人撤离前后路径差异；无持续辅助必要时不强加助手 |
| 城市 | 引导人员、保护后续交通、保持救援通路 | 交通保护服务覆盖人员过路窗口；接班时无服务空窗；新增受影响人员或响应成员退出 | 保护提前释放、替班晚到、合理保持原分工；区分服务已 ACK 与持续有效 |
| 餐厅 | 开业检查与两处证据汇总 | 先作为低耦合、同构可解的成本校准；新增检查区域/服务请求可测规模响应。要测异构，须另有业务上必要且可观测的不同工具/视角信息 | 单 Carter 完成应合法；空中观察只有带来不同业务信息才有价值，不能为了异构标签强制派飞 |

持续服务应记录 provider、beneficiary、服务开始/结束、所需窗口、实际覆盖区间、
允许中断和交接条件；重叠不足时记录实际业务后果。可靠技能负责内部执行，
模型负责选择何时启动、由谁接替、何时结束。允许服务完成请求后持续生效，
不必强迫模型逐仿真帧发命令。

停止低收益排障的规则：若问题只影响理想抓取底层精度、与分配/时序/资源约束无关，
